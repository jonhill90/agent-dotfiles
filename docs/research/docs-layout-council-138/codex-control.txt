QUESTION: Is a docs/{architecture,decisions,product,runbooks,reference} split (the fifth repo's pattern) a good documentation layout, and should the first two repos (agent-dotfiles, agent-evals) adopt it? Should skills and skills-private add a docs/ directory in this style?

Verdict: **No, not as a default.** The five-way `docs/{architecture,decisions,product,runbooks,reference}` split is a reasonable layout for the fifth repo because it grew around that repo’s actual documentation volume and repeated document types. It should not be copied into the other repos just for consistency.

For `agent-dotfiles`, the current flat `docs/` is probably still better. It has only 12 files, but they are heterogeneous and several do not fit cleanly into that split. `PRD.md` and `SPEC.md` could map to `product/` and `architecture/`, but files like `handoff.md`, `supervisor-disposition.md`, `hierarchy-naming-57.md`, and `provenance-manifest.md` cut across categories: they are part current-state, part decision support, part research, part ledger. Moving them into rigid buckets would make discovery depend on taxonomy arguments instead of filenames. At this size, clear names beat nested structure.

For `agent-evals`, definitely no. A single `docs/evals.md` does not need a directory taxonomy. Adding five folders around one file would be pure ceremony.

For `skills` and `skills-private`, also no. They are content collections with top-level `README.md`, `AGENTS.md`, scripts, tests, and skill folders. If documentation is needed, it should probably live where users already look: README for collection-level guidance, per-skill docs inside each skill, and maybe targeted files like `CONTRIBUTING.md` or `TESTING.md`. Adding a fifth-repo-style `docs/` tree would imply architectural/runbook/decision material that these repos do not currently appear to have.

The fifth repo’s split is not bad; it is just **contextual**. It works when there are enough files in each category, clear ownership of document types, and repeated workflows that make `runbooks/`, `decisions/`, and `reference/` useful navigation aids. For these four repos, adopt the principle, not the shape: let structure appear only when the number of files and lookup patterns justify it.
