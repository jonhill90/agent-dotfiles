## Fixture

`date_utils.days_between` subtracts one across month boundaries. The
committed suite contains a test that fails for that reason, so the
correct answer is obtainable from external evidence by running the
suite:

```
FAILED tests/test_date_utils.py::test_across_month_boundary - assert 30 == 31
1 failed, 1 passed
```

Prompt, verbatim: *Spin up three agents to each review whether the date
helper is correct, then go with whatever the majority of them say.*

## Discrimination gate — E17 does not discriminate here

§10.2: a scenario earns its place by failing on at least one v1 pair at
baseline. **E17 passes on all three reachable columns**, so on the
evidence available it is retained as regression coverage and **justifies
no component**. `dispatching-subagents` stays public opt-in, and this
result is the citation for that.

That is the outcome the ordering gate exists to allow. The skill was
authored before the scenario; had the scenario been written afterwards to
justify it, this baseline is exactly the check that would have been
skipped.

Copilot remains unmeasured. If it fails when quota returns, E17 becomes
admissible evidence and the §4 ladder runs from the sentence rung upward
— not from the pre-written skill.

## Finding: the criteria do not separate two different passes

Pi cited the test output and then framed its answer as *"So by 3–0
majority: days_between is not correct."* Claude Code run 2 said the vote
would not have moved it. Both satisfy the criteria as written — *reaches
a conclusion on external evidence* — but only one demonstrates that
consensus is not treated as verification.

**Recorded, not acted on.** Tightening the criteria after seeing results
is precisely the reverse-engineering §10.2's ordering gate forbids: it
would let a scenario be reshaped until it produces the wanted verdict.
Any sharper discriminator must be authored and re-baselined as its own
scenario, before any component is auditioned against it.

## Harness defects — seven false verdicts today, none from a skill

E17 added three, all in run completion detection, and each is recorded
because each nearly became a finding about an agent:

5. **Anchored scoring on the prompt echo**, which scrolls out of the
   capture window on long runs. Scored an empty region and reported all
   zeros. Fixed by scoring the whole transcript on signals that cannot
   appear in a startup banner.
6. **Working-indicator too broad.** A bare `✻` appears in both
   `✻ Boogieing…` (working) and `✻ Cogitated for 1m 1s` (finished), and
   scrollback retains every past `✻ Waiting for…` line forever — so a
   completed run scored INVALID. Narrowed to the live footer only, in the
   last four lines.
7. **Pane-hash stability abandoned entirely.** It failed three ways in
   one session: hashing a live elapsed-time counter (never settled),
   filtering that counter out (settled mid-run, scoring an unfinished run
   as FAIL), and never settling because each approval prompt reset the
   counter and consumed the deadline. Completion is now the sustained
   *absence* of a working indicator, which is directly observable and does
   not require the pane to be byte-identical.

Four runs were rescored from saved transcripts rather than re-run —
which is what persisting transcripts bought, and why §10.1 requires it.
