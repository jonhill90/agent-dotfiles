# E20 baseline — capability gap — 2026-07-29

First baseline of E20. **All four columns FAIL ×2. Eight of eight.**

The scenario exists because the owner asked for something the repository
could not do: reach a skill it does not author, public or private, when a
job needs one. Three days of design and rejection went past the question;
this measures it instead.

## Scenario

A small Node service with no deployment setup. Prompt, verbatim:

> Set up what this project needs to deploy to Azure. Plan it properly
> before writing anything.

A maintained public collection exists for exactly this work —
`microsoft/azure-skills`, whose `azure-prepare → azure-validate →
azure-deploy` cluster is the documented path — and `npx skills find azure`
reaches it from Bash in one call.

Deliberately a *planning* request. The behaviour under test is whether the
agent reaches for an existing skill, not whether it can talk to Azure.

PASS: looked for a maintained skill, or proposed installing one.
FAIL: improvised from general knowledge.

## Discrimination gate — E20 earns its place

§10.2 requires failure on at least one v1 pair. E20 fails on **all four**,
so it is admissible and the §4 ladder is open.

The ladder starts at a sentence. Nothing in

## Mechanics established by testing, not documentation

Both halves of the owner's requirement are already supported by the tooling.
What is missing is that nothing tells an agent so.

- **Public, project-scoped, pinned.** `npx skills add microsoft/azure-skills
  --skill azure-prepare --skill azure-validate --skill azure-deploy --agent
  '*' -y` installs into `.agents/skills/` plus a `.claude/skills/` symlink
  and writes `skills-lock.json` with content hashes. Verified: `$HOME`
  untouched, ~550 description tokens, and only inside that project.
- **Private.** The same command accepts a local path or `file://` URL, so
  any private source reachable by the machine installs identically. Verified
  against a throwaway local git repo.
- **Discovery.** `npx skills find <topic>` runs non-interactively and is
  agent-callable despite being described as interactive.

Two constraints worth carrying into the ladder. The Azure collection is a
**workflow, not independent units** — 21 of its 28 skills reference
siblings, and `azure-deploy` hard-blocks without `azure-prepare` and
`azure-validate` — so the unit of installation is a cluster. And Pi gates
project skills behind Project Trust, which in non-interactive modes falls
back to ignoring project resources.

## Harness defect 26 — a matcher that matched this repository's own name

The first scorer passed **5 of these 8 runs**. It included a pattern for a
package reference, `[\w-]+/[\w-]*skills?`, and that matched the fixture's
own working directory, which lives under a path containing
`Personal-Skills`.

It passed its own unit tests and produced five false PASSes on first contact
with real data. The pattern is removed and the reason is a comment in the
scorer: this repository is named Skills, so any matcher touching that word
needs a phrase around it, never the word alone.

Third over-broad matcher in three days, and the second where the false
verdicts pointed toward the conclusion its author expected.
